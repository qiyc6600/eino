# Agent 系统架构说明

本文从 Agent 项目的角度介绍系统架构，重点说明登录用户权限管理、人机协同、多 Agent 与工具调用、上下文管理和记忆管理五个模块是怎样实现的，以及它们如何共同完成一次用户请求。

文档以系统行为和业务流程为主，不展开具体代码变量和接口定义，适合用于项目汇报、架构评审和开发人员快速理解系统。涉及框架能力时，统一采用任务要求中的术语，如 sessionId、RBAC、工具级 ACL、interrupt/resume、CheckpointStore、ToolRegistry、ReActAgent、supervisor、TokenCounter、短期记忆和长期记忆。

---

## 一、项目整体定位

这个项目不是一个只负责问答的聊天机器人，而是一个具备身份识别、权限控制、任务分工、工具执行、人工审批、上下文压缩和长期记忆能力的 Agent 系统。

普通聊天机器人通常只需要把用户问题发送给大模型，再把模型回答返回给用户。本项目在这个过程之外增加了一套执行控制机制。系统不仅要理解用户想做什么，还要判断当前用户是谁、是否有权执行某项操作、是否需要人工批准、应该由 supervisor 分派给哪个子 Agent、历史信息是否过长，以及哪些用户偏好需要在后续会话中继续使用。

因此，系统可以理解为由三个部分组成。

第一部分是交互与接入层。浏览器页面负责登录、聊天、展示工具执行过程、显示审批卡片和查看用户记忆。后端接口负责接收这些请求，并在进入 Agent 之前完成身份校验。

第二部分是 Agent 运行层。它负责组装当前请求需要的提示信息和历史上下文，由 supervisor 将任务分派给不同的子 Agent。每个子 Agent 内部统一运行 ReAct 循环，也就是 Reason、Act、Observe，再回到 Reason，直到得到最终答案或遇到需要人工处理的中断。

第三部分是控制与状态层。权限系统决定工具能不能执行，人机协同系统决定高风险操作是否需要暂停，记忆系统保存运行状态和用户偏好，上下文系统则控制每次发送给模型的信息量。

从整体流程看，一次请求会依次经过身份认证、长期记忆读取、上下文整理、任务路由、工具权限检查、人工审批判断、工具执行、结果回传和记忆更新。五个核心模块都围绕这一条 Agent 执行链协同工作。

## 二、一次请求是怎样执行的

用户首先在页面中登录。登录成功后，系统会创建 Session 并返回 sessionId，前端在后续 Agent 调用中携带该 sessionId。每次请求到达后端时，系统都会重新校验 sessionId，并从服务端 Session 中取得用户身份和角色，而不是相信前端自行提交的用户信息。

身份确认后，系统读取该用户以前保存的偏好和与当前问题相关的历史记忆。例如，用户曾经表达过“回答请简洁”或者“优先使用 Go”，这些信息会在本次推理前加入 Agent 的背景信息中。

随后，系统取得当前对话线程的历史消息，并计算这些消息占用的上下文空间。如果历史较短，系统直接保留原始消息；如果历史接近模型的上下文上限，系统会把较早的对话压缩成摘要，同时保留最近的原始对话和完整的工具调用记录。这里有一个关键区分：**压缩只改变送给模型的内容，不改变保存的对话**——完整历史始终完整落盘，模型看到的才是摘要版本，因此不会出现"摘要的摘要"，用户回看也不会被摘要顶替。

整理后的信息会交给 supervisor。supervisor 是多 Agent 系统的中心路由，根据用户意图选择合适的子 Agent。数学问题交给数学 Agent，天气和日志查询交给搜索 Agent，订单和邮件等业务操作交给通用 Agent。

整个执行过程中，系统会把进展实时推送到页面：路由到了哪个子 Agent、正在调用哪个工具、工具是否完成、是否在等待人工审批，都会即时显示在输入框上方的一行状态里；模型生成的答案也按片段逐步显示，而不是等全部生成完再一次性出现。如果用户中途点击停止，系统会中断本次运行，并保留已经收到的内容。

子 Agent 接到任务后，会在 ReAct 循环中判断是否需要使用工具。如果需要，它会在 Act 阶段发出结构化 ToolCall。系统在真正执行 Tool 之前首先执行工具级 ACL 校验。无权限时，Tool 不会执行，拒绝原因会作为 ToolResult 回灌给 LLM，由子 Agent 解释或重新规划。

如果权限检查通过，系统继续判断该工具是否属于高风险操作。普通查询类工具可以直接执行；删除订单、发送邮件等高风险工具会暂停当前运行，向页面返回一条审批请求。用户批准后系统才执行工具，用户拒绝后则把拒绝原因交还给 Agent，让它重新规划或结束操作。

工具执行结果不会直接作为最终回复返回，而是先作为观察结果交给 Agent。Agent 可以根据结果继续调用其他工具，也可以组织成自然语言答案。整个推理和执行过程设有最大循环次数，防止模型反复调用工具而无法结束。过长的单条工具结果会被截断，避免一条冗长输出挤占整个上下文。

运行完成后，系统保存本轮对话，将可恢复的会话快照写入短期存储，并从用户消息中提取偏好写入长期记忆。下一次对话又会从这些状态开始，形成完整闭环。如果用户不希望被记忆，可以在记忆面板关闭开关——此后系统既不再从对话中提取新记忆，也不再把已有记忆注入提示词，已有条目保留但不再生效。

## 三、登录用户权限管理（身份与权限子系统）

### 1. 用户登录、Session 与 SessionStore

系统采用服务端 Session 认证。用户提交用户名和密码后，后端对凭证进行校验，校验成功便创建 Session、生成随机 sessionId，并在服务端记录该 Session 所属的用户、用户名、角色和登录时间。

除登录接口和静态页面外，其他接口都必须先校验 sessionId。认证成功后，系统把当前用户信息写入身份上下文，聊天、工具、节点、HITL 和记忆模块都从这个可信上下文中读取用户身份。身份上下文沿调用链透传，对 LLM 隐藏，对 Tool 和节点可见。

这种方式的关键点是，用户身份不会由大模型生成，也不会由工具参数决定。即使用户在聊天中声称自己是管理员，或者尝试在工具参数中伪造其他用户编号，也不会改变服务端已经确认的真实身份。

当前项目不预置账号或密码。空用户库通过环境变量创建初始管理员，后续不会覆盖已存在账户；访客账户由管理员按需创建。密码使用带随机盐的 Argon2id 保存；旧版 SHA-256 密码在成功登录后自动升级。Session 通过统一的 SessionStore 抽象进行创建、查询、删除、按用户列举和批量撤销，提供内存、单进程 JSON 文件和 PostgreSQL 多实例实现。

### 2. RBAC 角色与工具权限

权限管理采用 RBAC。用户可以拥有一个或多个角色，每个角色对应一组可以调用的 Tool，权限粒度达到工具级。

管理员可以使用全部工具，包括计算、天气、日志搜索、订单查询、订单删除和邮件发送。访客只能使用计算、天气和订单查询，不能搜索管理日志，也不能删除订单或发送邮件。

系统没有把权限判断分散到每一个工具内部，而是在 Agent 工具执行链上进行统一拦截。这样新增工具时，只需要声明工具对应的权限和角色关系，不需要在业务实现中重复编写用户判断逻辑。

### 3. Agent 场景下的工具级 ACL

系统对 Agent 工具调用采用三层控制，真正的权限拦截集中在框架层，不分散到各个 Tool 的业务逻辑中。

第一层是能力提示。系统在生成 Agent 提示信息时，只向模型描述当前角色可以使用的能力。这可以减少模型选择无权限工具的概率，但它只是引导机制，不能作为真正的安全边界，因为模型仍有可能产生错误调用。

第二层是调用检查。当 Agent 已经生成 ToolCall 后，执行器会在调用 Tool 或子 Agent 前再次执行 ACL 校验。如果用户对某个子 Agent 内的所有 Tool 都没有权限，系统会直接拒绝调用该子 Agent。

第三层是 Tool 执行边界。所有注册到 ToolRegistry 的 Tool 都会经过统一 ACL 包装。即使前面的提示或调用检查出现遗漏，Tool 在发生真实业务操作前仍会进行最终校验。

ACL 拒绝后，系统不会伪装成普通执行失败，也不会触发人工审批，而是生成包含拒绝原因的 ToolResult 并回灌给 LLM。Agent 可以据此告诉用户权限不足，或者选择当前角色允许的替代方案。

### 4. 多用户数据隔离

订单和长期记忆以 userId 作为用户范围，短期记忆以 userId 和 thread_id 作为隔离范围。订单 Tool 只能查询或修改当前用户的订单，记忆模块也只会读取当前用户自己的偏好。

这种隔离方式体现了一个重要原则：业务数据的用户范围必须由认证上下文决定，不能由模型或者客户端参数决定。

当前线程按 `(userId, thread_id)` 隔离，运行事件按所属用户读取，审批恢复也核对申请人身份。用户和角色管理由管理员权限保护。模型切换仍是进程级配置；如果部署多个实例，需要另行协调各实例的模型选择。

生产环境还应结合实际组织角色，细化审批人、申请人与运维人员对具体资源的权限。

### 5. 生产环境需要增强的内容

密码已使用 Argon2id，Session 支持过期、滑动续期和按用户撤销；角色变化后所有旧会话失效。登录失败按用户名和直接连接 IP 限流。生产环境仍应补充设备管理，并优先使用 Secure、HttpOnly、SameSite Cookie 配合 CSRF 防护。当前 sessionId 通过 Authorization 请求头传递，不接受 URL 查询参数。

此外，权限体系可以从当前的“角色控制工具”继续扩展为“角色控制接口、工具和具体资源”。例如，普通用户可以申请删除自己的订单，但只有指定审批人员能够批准；运维人员可以查看运行记录，但不能修改用户角色。

## 四、人机协同（Web 人机交互）

### 1. 人机协同的作用

大模型擅长理解意图和制定计划，但不应该在没有控制的情况下直接执行所有真实操作。查询天气和计算表达式通常风险较低，而删除数据、发送邮件、修改配置等操作可能造成不可逆影响。

人机协同模块在模型决策和真实执行之间增加了人工控制点。Agent 可以主动提出操作，但最终是否执行由系统策略和人工决定。

本项目采用异步 HITL 方式。Agent 运行到暂停点或审批闸门后，不会一直占用请求等待，而是执行 interrupt：携带待决策 payload，保存当前状态，并立即向 Web 动态页面返回“已中断”。用户稍后作出批准或拒绝决定，系统再通过 resume 从保存状态恢复执行。

### 2. 工具级 interrupt/resume

每个工具都会声明自身风险等级以及是否需要审批。计算、天气查询和订单查询属于普通操作，可以在权限通过后直接执行。删除订单和发送邮件属于高风险操作，必须先暂停。

当子 Agent 生成高风险 ToolCall 后，系统先执行工具级 ACL。只有用户确实拥有该 Tool 权限时，才会在 Tool 调用前 interrupt。审批 payload 会记录操作类型、工具参数、所属用户、thread_id、run ID 和风险说明，并在 Web 动态页面展示。

如果用户批准，系统根据同一个 run ID 读取状态，使用原来的参数执行尚未执行的 Tool，然后把 ToolResult 回灌给 LLM。Agent 会根据真实结果继续 ReAct 并生成最终回复。

如果用户拒绝，工具不会执行。系统会把“用户拒绝了该操作”以及可选的拒绝原因作为观察结果交给 Agent。这样 Agent 可以自然地回复“操作已取消”，也可以根据拒绝原因提出其他方案。

这种设计比在模型回复中简单询问“是否确认”更可靠。普通文字确认完全依赖模型自行理解，而工具调用前的审批闸门由框架执行器强制控制，模型无法绕过。

### 3. 任意节点的 interrupt/resume

除 Tool 调用处的中断外，框架还提供统一的节点级 interrupt 入口，可以在编排流程的指定节点携带 payload 并保存状态。当前演示将暂停点设置在计划生成节点：请求设置 `confirmBeforeExecute` 后，系统会在模型生成执行计划之后、执行任何 Tool 之前 interrupt。

页面会向用户展示 Agent 准备执行的操作。用户批准意味着同意按照该计划继续，用户拒绝则意味着取消当前计划，并把拒绝信息交还给 Agent 重新规划。

节点级中断适合多个 Tool 组成的任务。例如，用户希望先查询订单，再根据状态发送通知。系统可以先展示完整行动计划，而不是在每个低风险步骤上都单独询问。

### 4. CheckpointStore 与恢复语义

为了让 Agent 在审批后继续工作，系统通过 CheckpointStore 保存当时的完整运行状态。CheckpointStore 提供状态的 save、load 和 delete 能力，默认使用内存版实现。保存内容不仅包括聊天文本，还包括已经执行到第几步、模型刚刚生成了哪些 ToolCall、哪些 Tool 仍在等待执行、当前运行是否完成等信息。

恢复时，系统先核对审批请求所属用户，再从该审批记录保存的完整状态快照恢复，把人工决定应用到状态中。批准时执行原操作，拒绝时写入拒绝反馈，然后重新进入 ReAct 循环。CheckpointStore 同时保留对应快照。

工具级中断发生在 Tool 真正执行之前，因此批准后的语义是从 Checkpoint 恢复对话和待执行调用，再使用原参数调用 Tool，而不是从某一行函数内部继续。危险 Tool 需要使用 run ID 和工具调用标识保证幂等。节点级中断的目标语义是从已保存节点状态进入后续节点；拒绝时进入拒绝分支或让 LLM 重新规划。

审批状态缺失或与运行标识不匹配时，系统会报错并停止恢复，避免从线程历史猜测原操作后重复执行。

### 5. 多 Agent 中的审批传递

高风险操作通常发生在子 Agent 内部。例如，supervisor 把任务分派给通用 Agent，通用 Agent 又决定调用删除订单 Tool。

此时 interrupt 不能只停留在子 Agent 内部，否则外层 supervisor 可能把它当成普通错误。项目会把子 Agent 内产生的中断信号向上传递，最终由统一 HITL 模块创建审批请求。

审批完成后，系统把 ToolResult 转换成子 Agent 任务的观察结果，再交给外层 supervisor 汇总。这样无论高风险操作出现在 supervisor 还是子 Agent 中，用户看到的 interrupt/resume 体验都是统一的。

### 6. 当前实现需要完善的地方

审批记录、Checkpoint 和线程历史可使用 PostgreSQL 跨实例共享。三者全部选择 PostgreSQL 时，创建中断的写入在同一事务中提交；审批恢复后的旧审批凭据、运行事件和最终线程或下一条审批也一起提交。数据库写入失败会回滚收尾状态并保留 `running` 认领，避免自动重放可能已执行的工具。内存、文件或混合后端不具备这项跨存储事务保证。

当前系统还没有完整区分申请人和审批人。更严格的业务场景需要支持指定审批角色、禁止申请人自批、审批超时、撤销、多人会签和完整审计记录。

计划级中断的开关由每次聊天请求单独传入；批准后从保存的待执行工具状态继续。

如果一次恢复过程中再次遇到新的高风险动作，执行器会生成新的审批请求，并沿用同一运行 ID 继续等待下一次决定。

## 五、多 Agent 与工具调用（编排与工具子系统）

### 1. supervisor 中心路由模式

如果把所有提示、Tool 和业务规则都交给一个 Agent，随着功能增加，模型需要同时理解的内容会越来越多，工具选择也更容易出错。

本项目按照任务要求只采用 supervisor 模式进行多 Agent 协作。supervisor 是中心 Agent，负责理解用户需求、路由分派和最终结果汇总；子 Agent 只关注本领域任务和本领域 Tool。

当前系统包含三个子 Agent。

数学 Agent 负责算术和数学计算，只能使用计算 Tool。搜索 Agent 负责天气查询和日志搜索，可以使用天气和日志 Tool。通用 Agent 负责订单查询、订单删除和邮件发送，内部包含相应的业务规则，并配合工具级 ACL 和 HITL 处理高风险操作。

这种结构使每个 Agent 的职责、提示和 Tool 范围都比较清晰。后续增加新领域时，可以继续添加新的子 Agent，而不必把所有规则都堆到一个提示中。

### 2. supervisor 的实现方式

项目使用 Eino 框架提供的 AgentAsTool 能力，把子 Agent 包装成 supervisor 可以调用的特殊 Tool。对于 supervisor 而言，选择子 Agent 和选择普通 Tool 的形式相似；对于系统而言，被调用的对象实际又是一个运行独立 ReAct 循环的 Agent。

supervisor 接收用户的完整问题，根据各子 Agent 的职责描述生成中心路由选择。子 Agent 完成任务后，将结果交回 supervisor，由 supervisor 汇总形成最终答复。supervisor 对外仍表现为一个统一执行入口的 Agent。

每个子 Agent 都使用 fresh context，其中只包含该子 Agent 的职责说明和当前任务，不直接继承 supervisor 的全部内部上下文。这种上下文隔离可以降低不同领域指令互相干扰的概率。

### 3. ReActAgent 与 MaxIterations

所有子 Agent 内部统一复用 ReActAgent 的执行逻辑，即 Reason、Act、Observe，再回到 Reason。

在 Reason 阶段，LLM 阅读当前问题、历史和已有 ToolResult，决定直接回答还是调用 Tool。在 Act 阶段，LLM 发出结构化 ToolCall，系统对其进行权限、风险和参数处理。在 Observe 阶段，ToolResult 被序列化为工具消息并回灌对话历史，随后再次进入 Reason。

例如，用户要求查询某个订单时，通用 Agent 先生成订单查询 ToolCall。Tool 返回订单状态后，Agent 读取 ToolResult 并生成自然语言说明。如果用户要求删除订单，Agent 会生成删除调用，但执行器会先 interrupt；批准并执行后，删除结果才会进入 Observe 阶段。

系统设置 MaxIterations 兜底，当前最多执行二十步，防止模型在 Tool 之间无限循环。超过上限时终止 ReAct 循环，并返回“已达迭代上限”的合理提示。

### 4. Tool 抽象与 ToolRegistry

系统设计了统一 Tool 抽象。每个 Tool 对外提供名称、描述和 JSON Schema，对内封装真实业务逻辑，并返回包含内容、错误和元数据的结构化 ToolResult。所有 Tool 统一注册到 ToolRegistry，ToolRegistry 支持注册、查询和按名称调用；Agent 启动时从中获取工具集并提供给 LLM。

项目当前提供六个示例 Tool：计算器、天气查询、grep、订单查询、订单删除和邮件发送。其中查询类 Tool 主要展示信息获取流程，订单删除和邮件发送主要展示高风险动作的 HITL 流程。

Tool 通过统一适配层接入 Eino。LLM 只需要输出符合 JSON Schema 的 ToolCall，适配层负责从身份上下文取得当前 userId 和角色，再按名称从 ToolRegistry 调用真实 Tool。

ToolResult 统一表达成功、业务错误、ACL 拒绝、人工拒绝和系统错误。无论是哪种结果，都会作为 Observe 回灌给 LLM，使 ReActAgent 有机会继续规划，而不是简单中断整个对话。

### 5. 模型切换

系统支持在运行期间切换 Mock、DeepSeek、通义千问和 OpenAI 等模型。切换后会重新创建 supervisor、子 Agent、ReAct 执行器、摘要器和记忆提取器，但继续使用原来的 Tool、权限规则和内存状态。

这说明模型层与业务工具、权限和记忆之间保持了相对独立。更换模型不会改变用户能够执行哪些操作，也不会绕过审批规则。

### 6. 可观测性

系统会记录 Agent开始和结束、调度路由、工具完成、权限拒绝和上下文压缩等运行事件，并把事件随运行结果提供给前端。

当前事件主要用于演示和调试，部分已经定义的模型调用和审批事件还没有在所有执行路径中完整记录。生产环境应进一步接入统一日志、链路追踪、工具耗时、模型耗时、令牌消耗、费用统计和审计平台。

## 六、上下文管理（上下文窗口子系统）

### 1. 上下文包含什么

Agent 每次调用模型时看到的信息主要包括四部分。

第一部分是 system 消息，包括当前 Agent 的职责、允许使用的能力以及必须遵守的 Tool 调用要求。第二部分是用户长期偏好，例如回答语言、回答风格和偏好的技术方案。第三部分是当前 thread_id 的历史消息。第四部分是本轮用户输入。

这些信息共同决定模型如何理解本次请求。身份、角色和真实用户编号本身不会直接交给模型作为可修改数据，而是保留在服务端执行环境中。

### 2. 为什么需要上下文压缩

大模型能够接收的上下文长度有限。随着对话轮数增加，历史消息、工具参数和工具结果会不断占用空间。如果不进行管理，请求最终可能超过模型限制，或者大量陈旧内容影响当前推理。

项目按照任务要求实现了“保留最近 N 条消息”和“保留最近 N 个 Token”两种滑动窗口策略，同时实现 LLM 摘要压缩和 tool_call/tool 结果配对保护。当前聊天主流程主要使用 Token 预算和摘要压缩；按消息数裁剪已经实现，但还没有接入主要执行链。

### 3. TokenCounter 和触发条件

系统通过 TokenCounter 估算单条和多条消息占用的 Token 数量。可用的消息预算不是窗口的全部，而是从窗口上限中扣除工具定义开销和为模型回答预留的空间；当估算使用量超过可用预算的一定比例时触发摘要压缩，比例可以配置。

TokenCounter 使用轻量估算方法，中文主要按字符数量估算，英文主要按单词数量估算，并增加消息格式开销；除消息正文外，它还会计入工具调用的名称与参数——这部分在 ReAct 循环里增长最快，早期只统计正文会明显低估。它可用于演示和提前控制长度，但不等同于具体模型的官方 tokenizer。

工具定义的开销会单独估算：绑定给模型的 JSON schema 每次请求都会重发，只统计消息的计数器看不见它。除此之外，系统还会限制单条工具结果的长度，并在界面上同时展示本地估算值与模型服务商返回的实际用量——后者才是权威数字。

如果对长度控制要求严格，仍应针对每个模型使用对应的真实分词器。

### 4. 历史摘要

触发压缩后，system 消息永久保留。系统将较早的大约三分之二对话交给 LLM 生成摘要，同时保留最近大约三分之一原始消息。

摘要要求保留用户目标、已经确认的事实、重要工具结果、尚未完成的事项、权限和审批信息以及用户偏好，同时删除寒暄、重复内容和无关细节。

如果摘要模型调用失败，系统会自动改用规则方式提取旧消息中的主要内容，保证摘要功能故障不会阻塞 Agent主流程。

摘要完成后，系统还会再次按照令牌预算裁剪，确保最终上下文尽量控制在模型窗口内。当前配置中虽然提供了摘要目标长度，但压缩算法尚未严格按照该长度限制摘要，这一点可以在后续完善。

### 5. tool_call 与 tool 结果配对保护

工具调用在对话中通常由两部分组成：LLM 发出的 tool_call，以及 Tool 执行后返回的 tool 结果。这两部分必须成对出现。

如果裁剪时只保留 tool 结果而删除了原始 tool_call，LLM 不知道结果从何而来；如果只保留 tool_call 而删除结果，LLM 可能误以为 Tool 仍未执行。两种情况都可能造成模型接口报错或错误规划。

因此，系统在裁剪后会检查 tool_call 和 tool 结果是否完整配对。发现孤立消息时，会删除不完整部分，只向 LLM 保留完整的工具交互记录。

### 6. 对话线程管理

运行完成后，系统会把用户消息和最终回答保存到当前 thread_id。下一轮请求会读取同一 thread_id 的历史，从而形成连续对话。

这里需要区分两份内容：**保存的对话**始终是完整的原始消息，**送给模型的上下文**才可能是压缩后的摘要加近期消息。压缩结果只存在于本次运行送给模型的视图里，不会写回线程存储。这样做的原因是：如果压缩结果直接覆盖历史，原始对话会被摘要永久替换，而且下一轮的摘要会被当作普通助手消息再次参与压缩，形成"摘要的摘要"，语义逐轮衰减。

代价是线程历史会持续增长——模型输入由压缩保证有界，但存储没有保留上限，这是当前实现的一个已知限制。

当前线程存储在应用内存中，并且主要按照线程编号区分。生产环境应建立独立的对话线程存储，以用户和线程共同作为隔离条件，同时保留原始消息和供模型使用的派生摘要，便于审计和重新生成上下文。

## 七、记忆管理（记忆子系统）

### 1. 短期记忆与长期记忆分层

在 Agent 系统中，“历史消息”“运行快照”和“用户记忆”经常被统称为记忆，但它们的用途和生命周期并不相同。

对话上下文保存当前线程中的连续消息，目的是让下一轮对话理解前文。它通常只在同一个对话线程中使用。

短期记忆（Short-Term Memory）保存 Agent 在当前会话中执行到什么位置，目的是在审批或异常后恢复。它以 thread_id 为隔离粒度，与当前会话生命周期绑定，不应该自动影响其他会话。

长期记忆（Long-Term Memory）保存用户跨会话仍然有效的画像、事实和偏好，例如偏好的编程语言、回答风格或默认城市。它以 userId 作为命名空间，可以在不同 thread_id 之间复用。

项目将这几类状态分别存储，而不是使用同一个数据结构混合处理。

### 2. 短期记忆与 CheckpointStore

短期记忆通过 CheckpointStore 保存状态检查点。每个 Checkpoint 关联 userId、thread_id、run ID 和执行步骤，并保存可序列化的完整 Agent 状态。

它主要承担两个任务。第一个任务是保存人工审批发生时的 Agent状态，使系统能够在批准或拒绝后继续执行。第二个任务是在对话完成后保存消息快照，为服务异常后的会话恢复提供基础。

当前默认使用 InMemoryCheckpointStore，无需外部依赖即可完成 save、load 和 delete。CheckpointStore 与具体存储方式分离，因此可以平滑替换为数据库或分布式缓存。不过，应用启动时目前还不会自动把历史 Checkpoint 恢复到对话线程中，这部分仍需要增加完整的加载流程。

### 3. 长期记忆与 MemoryStore

长期记忆通过 MemoryStore 以事实条目的形式保存用户画像和偏好，并提供 put、get 和删除等能力。每条记忆包含所属 userId、偏好名称、偏好值、信息来源和更新时间。

用户可以通过记忆管理页面主动添加和删除偏好，系统也会在每轮聊天结束后自动分析用户消息。默认后端为 InMemoryMemoryStore，与 InMemoryCheckpointStore 相互独立，无需外部依赖即可完成跨会话记忆演示。

自动分析先执行确定性规则，再使用大模型补充。规则可以识别常见的编程语言、开发框架、编辑器、回答风格、回答语言、默认城市和输出格式。大模型负责提取规则没有覆盖但用户明确表达的偏好。

如果规则已经确定了某项偏好，大模型不会再次覆盖它。这样可以兼顾确定性和覆盖范围，避免完全依赖模型自由生成记忆。

下一次请求开始时，系统通过 userId 从 MemoryStore 读取当前用户的偏好，并整理成背景信息交给 Agent。因此，用户在会话 A 中表达“我喜欢用 Python”，新建不同 thread_id 的会话 B 后，Agent 仍能读取该偏好并优先使用 Python。

### 4. 长期记忆的语义检索扩展

MemoryStore 中的偏好事实适合保存明确记忆，但无法覆盖所有历史内容。作为基础任务之外的扩展，系统还提供长期记忆的语义检索能力，让 Agent 能够根据当前问题查找相关旧消息。

每轮用户原始消息会被转换成向量并保存到该用户自己的记忆空间。处理新问题时，系统使用当前问题进行相似度检索，取最相关的三条历史，并过滤相关度过低的结果。

检索结果会以“用户历史相关记忆”的形式加入本轮背景信息。这样即使某段历史没有被提取成明确偏好，只要与当前问题语义相关，仍有机会被 Agent重新利用。

默认实现采用本地哈希方式生成简化向量，不依赖外部服务，适合演示。它主要依靠词语和字符重合，不具备真正的深层语义理解。系统也支持使用本地 Ollama 或兼容 OpenAI 的嵌入模型，并使用进程内向量数据库进行相似度检索。

无论采用哪种后端，向量数据都按用户划分空间，查询时只在当前用户自己的记忆中搜索。

### 5. 记忆的写入和读取闭环

用户消息完成一次 Agent运行后，会同时进入两条记忆路径。

一条路径提取明确偏好并写入 MemoryStore。另一条路径保留原始消息并写入向量记忆。

下一轮请求开始时，MemoryStore 中的偏好事实直接加入 Agent 背景，向量记忆则根据当前问题动态检索后加入背景。两者结合后，系统既能稳定保留明确偏好，也能按需找回相关历史。

### 6. 隐私和生产化要求

自动长期保存用户消息会带来隐私风险。生产系统应明确告知用户哪些信息会进入长期记忆，并提供关闭、查看、修改、导出和彻底删除能力。

当前实现已经提供了其中一部分：记忆面板可以查看、新增、修改和删除条目，也提供了按用户粒度的"禁止记忆"开关——关闭后既不提取新记忆也不注入已有记忆，已有条目保留而不删除，用户可以随时恢复。开关的判断位于记忆服务内部，任何调用路径都无法绕过，因此不存在某个入口漏掉判断的情况。

记忆写入前还应识别密码、身份证件、银行卡、访问密钥等敏感信息。检索结果加入模型上下文前，应标记来源和可信度，并防止历史消息中的恶意提示影响系统规则。

此外，生产环境不宜无条件把所有偏好和检索结果加入提示中，而应设置记忆数量、令牌预算、时间衰减、相关度阈值和冲突处理规则。当前实现已具备令牌预算、时间衰减、重要度与相关度打分和冲突消解，敏感信息识别与提示注入防护仍待补充。

## 八、五个模块怎样协同

登录用户权限管理是整个系统的入口。它确定请求来自哪个用户，并为后续所有数据访问和工具调用提供可信身份。没有这一层，记忆隔离、审批归属和订单隔离都无法成立。

上下文管理和记忆管理共同为 Agent提供推理材料。上下文管理关注当前线程中“哪些历史应该进入本轮模型”，记忆管理关注跨运行、跨线程的信息“应该保存多久、什么时候重新取回”。

多 Agent 模块负责理解任务和选择行动。supervisor 完成中心路由和结果汇总，子 Agent 在 fresh context 中运行 ReActAgent，生成具体 ToolCall，并根据 ToolResult 继续推理。

工具级 ACL 和 HITL 构成 Tool 执行的安全边界。ACL 先判断当前用户是否可以调用，HITL 再判断允许调用的 Tool 是否必须 interrupt 并由人批准。只有两层都通过后，真实 Tool 才会执行。

ToolResult 作为 Observe 回灌 ReAct 循环，最终答案写回当前 thread_id。用户消息中稳定的偏好进入长期记忆，运行状态和会话快照进入短期记忆，供后续会话或 interrupt/resume 使用。

因此，五个模块之间的核心关系可以用一句话概括：

> Session 与 RBAC 确定“谁在操作、能调用哪个 Tool”，supervisor 与 ReActAgent 决定“任务交给谁、下一步做什么”，ACL 与 HITL 控制“能不能执行、何时执行”，上下文与记忆系统保证 Agent“知道哪些过去的信息”。

## 九、当前架构的特点

第一，系统把模型推理和业务执行分开。模型负责理解和规划，服务端负责身份、权限、审批和真实副作用。即使更换模型，安全规则仍然有效。

第二，系统把高风险操作的审批放在工具执行边界，而不是依赖模型主动询问用户。这使审批成为不可绕过的执行规则。

第三，系统通过 supervisor 和子 Agent 实现职责拆分。新增业务领域时，可以独立增加子 Agent 和 Tool，不需要持续扩大单一 Agent 的提示。

第四，系统明确区分对话上下文、运行检查点、结构化偏好和语义记忆，避免不同生命周期的状态相互污染。

第五，主要存储都通过抽象方式与业务逻辑分离。当前虽然使用内存实现，但后续可以逐步替换为数据库、缓存和向量数据库。

## 十、从演示系统到生产系统的演进建议

**第一阶段：安全边界（已完成）**。所有线程、运行、审批和用户管理接口都验证当前用户是否拥有资源或管理权限，对话线程按用户和线程共同隔离，且隔离由存储层统一强制（`CheckUserScope`），不依赖各调用点自觉。

**第二阶段：人机协同（部分完成）**。计划级中断的状态保存顺序已修正，恢复过程中再次产生审批（连续审批）已支持，审批凭据与业务结果的一致性通过事务与"结果不确定时禁止重放"保障。**待补**：审批角色、超时、撤销、会签和审计能力。

**第三阶段：状态持久化（已完成）**。会话、对话线程、运行快照、审批请求、用户记忆和幂等结果都可迁移到可靠存储（文件或 PostgreSQL），支持重启恢复与多实例部署；PostgreSQL 侧使用版本化迁移、线程级 advisory lock 与审批原子认领。

**第四阶段：可观测性（部分完成）**。已记录模型路由、工具调用与令牌消耗（含服务商返回的实际用量），运行事件可跨实例读取并设有保留期。**待补**：统一链路编号、各阶段耗时、费用统计，以及不可篡改的审计记录。

**第五阶段：上下文与记忆治理（部分完成）**。已具备令牌预算、时间衰减、相关度阈值、冲突消解，以及用户级的记忆开关。**待补**：真实分词器、摘要的来源与版本、检索结果的长度上限、数据导出与彻底删除能力。

**此外，工程交付层面已经补上了持续集成**：检查逻辑收敛到 `scripts/check.sh`（本地与 CI 共用），`.github/workflows/ci.yml` 运行 Go 检查与前端语法两个并行任务。前端语法之所以单列一个任务，是因为 `go:embed` 不校验 JS——本项目曾出现过语法错误让整个页面失去交互、而全部 Go 测试仍然通过的情况。

## 十一、总结

从 Agent 项目的角度看，这套系统是一个以 supervisor 中心路由和子 Agent ReAct 循环为推理核心，以 ToolRegistry 为行动能力，以 Session、RBAC、工具级 ACL 和 HITL 为安全边界，以上下文窗口和分层记忆为状态基础的 Agent 应用框架。

登录用户权限管理保证系统知道当前操作者是谁以及他能够使用哪些能力；人机协同保证高风险动作在发生真实副作用前能够暂停和审阅；多 Agent与工具调用负责把复杂任务拆分并转化为实际行动；上下文管理保证有限的模型窗口中保留最有价值的信息；记忆管理则让重要状态能够跨步骤、跨线程和跨会话延续。

当前项目已经形成了这五个模块的主要执行闭环，适合作为 Agent 架构演示和后续工程化的基础。进入生产环境前，最重要的工作不是继续增加更多工具，而是补齐资源归属授权、审批状态一致性、持久化、审计和记忆隐私治理。
